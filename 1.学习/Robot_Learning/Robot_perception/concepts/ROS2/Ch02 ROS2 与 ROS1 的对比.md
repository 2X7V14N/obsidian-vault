# Ch02 ROS2 与 ROS1 的对比

> 来源：《ROS2 入门 21 讲》古月居 · 1.2 ROS2 对比 ROS1

**ROS2 不是 ROS1 的修修补补，而是一次"推倒重来"**——在借鉴 ROS1 成功经验的基础上，对系统架构和软件代码全部重新设计和实现。理解 ROS2 为什么存在、和 ROS1 差在哪，是进入 ROS2 世界的第一道门。

![[attachments/r12_image-20220523111754433.png]]

## ROS1 的局限性：Why ROS2？

ROS 最早的设计目标是开发 PR2 家庭服务机器人。这款机器人绝大部分时间独立工作，因此 ROS 当初的设计条件非常理想：

- **工作站级别的计算平台**，不担忧算力不够；
- **有线连接**，通信可靠、没有丢数据或黑客入侵风险；
- **成本高昂**，只用于学术研究。

但随着 ROS 普及，应用场景和 PR2 天翻地覆——要在资源有限的**嵌入式系统**中运行、要在**有干扰的环境**中保证通信可靠性、要**产品化走向市场**甚至用在自动驾驶和航天机器人上。原本针对 PR2 设计的软件框架逐渐暴露出问题。

![[attachments/r12_image-20220523112633134.png]]

## 全新的 ROS2：六大设计需求

ROS2 在设计之初就考虑到满足各种各样机器人应用的需求，怀揣变革智能机器人时代的历史使命：

1. **多机器人系统**：未来机器人不会是独立个体，机器人与机器人之间需要通信协作，ROS2 提供标准方法和通信机制。
2. **跨平台**：可运行于 Linux、Windows、MacOS、RTOS，甚至没有操作系统的微控制器（MCU）上。
3. **实时性**：为机器人运动控制和行为策略提供实时性保障——比如可靠地在 100ms 内发现前方行人，或稳定地在 1ms 周期内完成运动学/动力学解算。
4. **网络连接**：无论在怎样的网络环境下，尽量保障数据的完整性和安全性——WiFi 信号不好时数据尽力发送，有黑客入侵风险时对数据加密解密。
5. **产品化**：ROS2 不仅能用于研发，还能直接搭载在产品中走向消费市场，这对稳定性、强壮性提出巨大挑战。
6. **项目管理**：设计、开发、调试、测试、部署全流程的项目管理工具和机制。

要满足这些需求，难度远超手机系统——机器人千差万别，"如何适合尽量多的机器人，可能远比开发一个手机系统或电脑系统更加复杂"。

![[attachments/r12_image23-16532773958263.gif]]

## 推倒重来

面对 ROS1 的局限，开发者有两个选择：第一是在 ROS1 架构上修改优化——类似把毛坯房重新装修翻新，但受制于原本建筑格局，长远看不是最佳选择；第二是**推倒重来**。他们最终选择了后者。

与 ROS1 相比，ROS2 的变化体现在三大框架层面：

![[attachments/r12_image-20220523114359304.png]]

- **系统架构颠覆性变化**：ROS1 中所有节点都需在节点管理器 ROS Master 下工作，一旦 Master 出问题，系统面临宕机风险。ROS2 实现真正的分布式，不再有 Master，借助 DDS 通信框架为所有节点通信提供可靠保障。
- **软件 API 重新设计**：ROS2 结合 C++ 最新标准和 Python3 语言特性设计了更具通用性的 API。ROS1 代码无法直接在 ROS2 运行，但保留了类似使用方法，并提供大量移植说明。
- **编译系统升级**：ROS1 的 rosbuild 和 catkin 对大项目及 Python 项目编译链接常出错；ROS2 重新优化为 **ament 和 colcon**。

## 系统架构对比

![[attachments/r12_image26-16532775781034.png]]

上图中左侧是 ROS1，右侧是 ROS2。两者最明显的变化是 **Master**：

- **应用层**：ROS1 中 Master 像公司的 CEO，有且只有一个，消失则系统混乱。ROS2 请走了这个最不稳定的角色，节点通过 **discovery 自发现机制**找到彼此、建立稳定通信连接。
- **中间层**：是 ROS 封装好的标准通信接口，我们写程序时频繁与这些接口打交道（发布图像数据、接收雷达信息），客户端库再调用底层复杂的驱动和通信协议。
- **通信协议**：ROS1 依赖 TCP/UDP，ROS2 更换为更复杂也更完善的 **DDS 系统**。
- **进程内通信**：两者都提供基于共享内存的通信方法，只是名字不同。
- **系统层**：ROS1 主要安装在 Linux，ROS2 可选项多——Linux、Windows、MacOS、RTOS 都可以。

## DDS 通信与 RMW 中间层

ROS2 相比 ROS1 最大的变化除了省略 Master，就是通信系统。ROS1 基于 TCP/UDP 的通信系统频繁诟病于延迟、丢数据、无法加密等问题；ROS2 中的 **DDS（Data Distribution Service）** 功能丰富得多。

![[attachments/r12_image27.png]]

DDS 是物联网中广泛应用的一种通信协议（类似 5G），是一个**国际标准**，能实现该标准的软件系统并非唯一——OpenSplice、FastRTPS 等多家厂家提供，性能不同、适用场景不同。

但这带来一个问题：每个厂家的软件接口不同，切换 DDS 就要重写代码，不符合 ROS 提高软件复用率的目标。为此 ROS2 设计了 **ROS Middleware（RMW）**——指定一套标准接口（如何发数据、如何收数据、数据属性如何配置），厂家想接入 ROS 社区就按这个标准写适配接口，把自家的 DDS 移植过来。对用户而言，**某个 DDS 用得不爽，安装另一个并简单配置即可，程序一行都不用改**。

![[attachments/r12_image28-16532776651855.png]]

例如产品开发时先用开源版 DDS 满足基本需求，交付部署时再更换为商业版更稳定的 DDS，减少开发成本。

## 保留的核心概念

ROS1 应用广泛，全球有几百万开发者已熟悉其开发方式和概念。ROS2 **尽量保留了这些概念**，便于迁移：

![[attachments/r12_image-20220523114814371.png]]

节点、话题、服务、动作、参数等核心概念在 ROS2 中依然存在，意义几乎一致。

## 编码方式与命令行

- **编码方式**：ROS2 使用更多面向对象的实现方法和语言特性，难度有所提高，但程序更具可读性和可移植性，更接近真实企业的机器人软件开发。建议在项目开发中边用边学，而非死啃编程语言教程。

![[attachments/r12_image-20220523114851763.png]]

- **命令行**：ROS1 命令行相对分散，每个功能一个独立命令（rosrun 启动节点、rostopic 控制话题）；ROS2 大幅集成，**所有命令统一在 ros2 主命令下**——ros2 run 启动节点、ros2 topic 控制话题，功能更多。

![[attachments/r12_image-20220523114915528.png]]

## 小结

ROS2 因 ROS1 的局限而生，目标是满足多机器人、跨平台、实时性、网络可靠性、产品化、项目管理六大需求。它推倒重来，用 DDS 替代 Master + TCP/UDP，用 ament/colcon 替代 catkin，重新设计 API，同时保留了核心概念与接近的操作习惯，让开发者可以平滑迁移。
